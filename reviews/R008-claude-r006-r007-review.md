## 3. 看板安全（R007）

实测和代码审查的结果：

| 检查 | 结果 |
|---|---|
| 未登录访问 `/api/state` | 401 ✔ |
| 带令牌但 `Origin: http://evil.example` | 403 ✔ |
| `deskbell ui` 一次性票据登录 | 浏览器跳到干净的 `/ui`，URL 里不留票据 ✔ |
| 同一张票据重放 | 302 到 `/ui`，**不发 cookie** ✔ |
| `/mcp` 能否用 cookie 调用 | 不能，只认 Bearer ✔（cookie 只能访问看板接口） |
| 代理写的内容（标题、进度、汇总）注入脚本 | 模板插值统一用 `esc()`；Markdown 渲染器先转义再加格式 ✔ |
| 外部资源 | 无，CSP 是 `default-src 'none'` ✔ |

**P3（以后再说）**

- 会话 cookie 是 `HMAC(令牌, 固定串)`，没有过期时间，所有登录共用同一个值；“退出”只清浏览器端，服务端不作废。本机单用户场景可以接受，以后可以换成服务端随机会话加 12 小时过期。
- CSP 带了 `'unsafe-inline'`，所以 XSS 只能靠转义来防。现在的转义做得很规范；以后可以改成 nonce。
- SSE：每个订阅者的队列上限 128 条，满了就丢弃，鉴权也正确。但连接数没有上限，写 socket 时也没有超时（`settimeout(None)`）：如果某个客户端停止读取，对应线程会一直卡住。本机场景影响小，可以加写超时和连接数上限（比如 16）。
- **`wakeup_latency_ms` 的口径**：只有 MCP `deskbell_wait` 这条路径会记录（`mcp_server.py:650–660`），CLI 后台 waiter（Claude Code 待命用的就是它）不记录；而且它衡量的是“总线唤醒耗时”，也就是从发出通知到 wait 返回，不是“AI 开始干活”的时间。看板上的“⚡ 热唤醒 · 2 ms”容易被理解成端到端响应。建议：①CLI waiter 醒来后也上报一次；②另加一个更有意义的指标“认领耗时”，即从派发到对方 `pickup` 的时间差，看板优先显示它。

## 4. 看板外观反馈（关口 2）

### A 类：建议进入阶段 3 之前改

1. **“工作中”状态显示不对（已实测复现）**。演示结束、mission 已经 `completed`、三端名下任务都是 0 时，三张卡片仍然都显示蓝色“工作中”。`/api/state` 里这三端的 `status` 都是 `active`，看板把 `active` 直接映射成了“工作中”。建议改成：
   - `waiter_active` → 绿色“待命”；
   - 名下 `claimed + running > 0` → 蓝色“工作中”；
   - 最近活跃但没有任务 → 中性色“在线”；
   - 超过阈值没有活跃 → 灰色“离线”；陈旧 → 橙色。
2. **任务看板太挤**。四列等宽挤在左半边，任务卡片里的文字被压成一字一行，空列又占着大片空白。建议二选一：①任务看板占满整行宽度，时间线放到下面；②空列折叠成只显示列名的窄条。
3. **事件时间线在卡片中间被截断**（截图里 #3 只露出半张）。要么让面板随内容增高，要么在底部加渐隐遮罩和“显示更多”，不要硬切。
4. **重录录屏**。现在只有 30 帧、4 fps、共 7.5 秒，基本是从“空白”直接跳到“已完成”，看不到任务在各列之间流转，也看不到轮次表一格一格亮起来。建议演示脚本每步之间停 1–1.5 秒，用 ≥10 fps 录 30–40 秒。

### B 类：可以和阶段 3 一起改

5. 进行中 mission 上的“关闭 Mission”是实心红色按钮，太醒目，容易误点。平时用描边的次要按钮，红色只留在确认弹窗里。
6. 进度条在 100% 时仍是蓝色，改成绿色；配额低于 20% 时，配额条改成橙色或红色，不再沿用各端的主色。
7. 卡片副标题显示 `claude/`、`codex/`、`gemini/`（分支前缀），看起来像路径，容易困惑。改成“Claude.app · Code”这类说明，分支前缀放到悬停提示里。
8. 任务卡片里的进度文字没有渲染行内代码，反引号原样露出（例如 `` `<=` ``），复用汇总那里的 `inline()` 即可。
9. 截图里的配额 78% / 44% 是 `--seed-demo-ui` 造的演示数据，看板上应标注“演示数据”，避免被当成真实额度。
10. 免密打开：`deskbell ui` 在 daemon 没启动时应给出明确提示（“daemon 未运行，先执行 …”）；登录弹窗里加一句“在终端运行 `deskbell ui` 可免密打开”。

## 5. 新产品方向评估

### 5.1 用户原话（2026-11-19）

- 使用必须方便，不想手动折腾令牌；
- 希望后续能**封装成 macOS App**；
- 希望能做成**类似 Pachat（多 AI 群聊）甚至更好的交互式前端**，同时还能直接打开三个官方 App 看原生效果或历史记录，并且**实时同步**。

Antigravity 的提议是：先跑通 B / C 级，再把 `/ui` 升级成 `@peer` 群聊前端，加上只读监听三端本地记录做同步检索，最后用 Swift `WKWebView` 封装成菜单栏 `Consilium.app`。

### 5.2 总体判断

**方向对，先后顺序基本对，但有两处要调整，还有三件事必须先说清楚。**

**调整 1：菜单栏 App 提前到群聊之前做。** 它很薄（WKWebView 加一个菜单栏图标），却能一次解决三个已经存在的问题：

| 现有问题 | 原生 App 怎么解决 |
|---|---|
| 令牌麻烦（用户原话第一条） | App 自己读本机的 `auth.token`，请求时自动带上，**连票据都不需要**，打开即用 |
| 冷通知点了没反应（R005 3.6，纯标准库做不到） | 用 `UNUserNotificationCenter` 发**可点击的通知**，点一下直接打开对应 App 的深链 |
| daemon 的启停和状态 | 菜单栏图标显示三端状态灯；可以启动、停止 daemon，开关开机自启 |

本机有 Command Line Tools 里的 `swiftc`（没有完整 Xcode），可以不建 Xcode 工程，直接编译出一个小 App；本机自用只需 ad-hoc 签名（`codesign -s -`），不用公证。**风险**：未签名或 ad-hoc 签名的 App 申请通知权限时，系统行为可能不稳定，要先做个最小原型验证。

**调整 2：“实时同步”只能做成单向只读镜像，而且不是三端都能做。** 本机实际情况（只看了文件结构，没读内容）：

| 来源 | 本地格式 | 能不能做 |
|---|---|---|
| Codex 线程 | `~/.codex/sessions/**/rollout-*.jsonl`（30 个） | 能，JSONL，追加写，方便增量监听；支持深链 `codex://threads/<id>` 跳回原生 App |
| Claude Code 会话 | `~/.claude/projects/*/*.jsonl`（121 个） | 能，JSONL |
| Antigravity 对话 | `~/.gemini/antigravity/conversations/*.db`（每个对话一个 SQLite 库，带 WAL） | 技术上能只读打开，但表结构没有公开，升级后可能变；放最后，并做好格式变化时的降级 |
| Claude Chat / Cowork、ChatGPT 普通聊天 | 存在云端，本地没有完整记录 | **做不到**，不要承诺 |

另外三条硬边界：
- **只读，不往官方 App 里写**。官方 App 的历史只能看、只能跳转过去，不能在 Consilium 里改写或“同步回去”；在 Consilium 里发的消息，通过 deskbell 派给对方，对方 App 里会自然出现一个新会话或一条新消息。
- **隐私**：rollout 里可能有明文账号、令牌和工具输出（用户此前确认过 Codex 记录里含明文测试账号）。索引只存元数据和用户 / 助手的正文，不存工具输出；按项目开关、默认关闭；只存在本机；做一个脱敏过滤（看起来像密钥、令牌、密码的字符串一律打码）。
- **不读 Claude Code 的会话来做“实时转播”**，只做检索和“在原生 App 打开”。实时进展一律走 deskbell 的事件（`report_progress`），这是唯一可靠的实时来源。

**必须先说清楚的三件事**

1. **“群聊”里的 AI 到底在哪儿思考？** 有两种做法，产品体验和成本完全不同：
   - **A. 原生 App 当参与者（现在的 deskbell 路线）**：消息派到三个官方 App，由它们带着本地工具和项目上下文去干活。优点是“原生效果”、能真改代码；缺点是对方 App 必须有一个**醒着的会话**才能接话。
   - **B. 直接调模型 API 当参与者（Pachat 的做法）**：Consilium 自己调 API（用户已有 Gravitex 网关，可以调到三家的模型），聊天秒回、体验最像群聊；缺点是没有官方 App 的本地工具和历史，也不会出现在官方 App 里。
   - Claude 原先的建议是两种都支持。
   - **用户决定（2026-11-19，原话“只要原生 App”）：只做 A。** 群聊里的参与者只有三个官方 App，不接模型 API，不做 API 参与者。因此第 2 条“待命成本”的实测结果直接决定群聊的体验：没有醒着会话的一端，只能等冷通知把它叫起来。
2. **“待命”的真实成本。** Claude Code 的后台 waiter 等待时不消耗额度；但 Codex 和 Antigravity 要想随时接话，目前只能让一个会话循环调用 `deskbell_wait`（每次最多 300 s），每循环一次就是一次工具调用加一轮模型处理，会持续消耗额度（用户有“不要大批量消耗本机额度”的规则）。**阶段 3 必须实测**：每个 App 待命一小时消耗多少额度。如果太贵，Codex / Antigravity 就只在被 @ 时由冷通知叫起来。
3. **群聊不新造一套传输。** 一个 mission 就是一个群；用户发言是一种新事件 `user_message`；`@peer` 就是 `dispatch_task` 或 `request_review`；进度和结果就是现有事件。只加一张消息视图，不另起服务、不另建数据库。
